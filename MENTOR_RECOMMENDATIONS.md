# РЕКОМЕНДАЦИИ МЕНТОРА — КАК РЕАЛЬНО ПРОЙТИ ЭТОТ ПЛАН

> Этот документ — не часть учебного плана. Это набор принципов, без которых
> даже идеальный план провалится. Прочитай до начала обучения.

---

## 1. МЕТОДОЛОГИЯ ОБУЧЕНИЯ — КАК УЧИТЬСЯ ПРАВИЛЬНО

### 1.1 Правило 20/80 (Принцип Парето)
20% тем дают 80% результата. Вот эти 20%:
- Типы данных, условия, циклы, методы
- Классы, наследование, интерфейсы
- Коллекции (List, Dictionary)
- LINQ
- async/await
- Паттерны: MVVM, State, Observer, Singleton, Factory

**Не пытайся идеально выучить ВСЁ подряд.** Если тема не заходит — пометь её, двигайся дальше, вернёшься позже. Лучше пройти план на 70% глубины, чем застрять на модуле 2 навечно.

### 1.2 Техника Фейнмана
После каждой темы — объясни её вслух (или напиши в заметке) **простыми словами**, как будто объясняешь 10-летнему ребёнку. Если не можешь объяснить просто — ты не понял.

### 1.3 Активное вспоминание (Active Recall)
НЕ перечитывай материал. Вместо этого:
1. Закрой документацию
2. Попробуй написать код по памяти
3. Застрял → подсмотрел → закрыл → написал по памяти снова

Это в 3 раза эффективнее чем "прочитал и понял".

### 1.4 Интервальное повторение
- Через 1 день после изучения — повтори ключевые моменты (5 мин)
- Через 3 дня — ещё раз (3 мин)
- Через 7 дней — ещё раз (2 мин)
- Через 30 дней — финальная проверка

Заведи файл `REVIEW_LOG.md` и записывай что повторил.

### 1.5 Правило 2 минут
Если ты не можешь заставить себя сесть за учёбу — скажи "я просто открою проект и напишу 1 строчку кода". Через 2 минуты ты уже будешь вовлечён. Это работает на нейрохимии — начало действия снижает сопротивление.

### 1.6 Pomodoro
- 25 минут учёба → 5 минут перерыв
- После 4 циклов → 15-30 минут большой перерыв
- Во время перерыва — ВСТАНЬ, походи, попей воды
- НЕ листай телефон в перерыве — мозг должен отдыхать

## 2. КРИТИЧЕСКОЕ ИЗМЕНЕНИЕ ПОРЯДКА ОБУЧЕНИЯ

### Проблема текущего плана:
4 недели чистой теории C# до первого реального проекта — это убийца мотивации.

### Решение: Спиральное обучение
Вместо "сначала вся теория, потом практика" — делай так:

```
Неделя 1: Основы C# (1.1-1.4) + Создай первое Godot-приложение (двигающийся квадрат)
Неделя 2: Строки, массивы + Создай первое Uno-приложение (калькулятор)
Неделя 3: Методы + Улучши Godot-игру (враги, столкновения)
Неделя 4: ООП основы + Улучши Uno-приложение (классы, привязка данных)
...и так далее
```

**Ключевая идея:** На каждой неделе — кусок теории + реальное применение на платформе. Ты ВИДИШЬ результат каждую неделю. Это топливо для мотивации.

### Конкретный недельный ритм:
```
Понедельник:  Теория C# (новая тема) — 2 часа
Вторник:      Мини-упражнения по теме — 1.5 часа
Среда:        Практика Godot (применение темы) — 2 часа
Четверг:      Практика Uno Platform (применение темы) — 2 часа
Пятница:      Средняя задача + контрольные вопросы — 1.5 часа
Суббота:      Свободный день: улучшай любой проект или исследуй интересное
Воскресенье:  Повторение (Active Recall) за неделю — 30 мин
```

## 3. ПРОЕКТЫ-СПУТНИКИ — ВМЕСТО РАЗРОЗНЕННЫХ ЗАДАЧ

### Проблема:
В плане 50+ отдельных маленьких проектов. Это значит 50 раз: создать проект, настроить, начать с нуля, бросить.

### Решение: 2 проекта-спутника, которые растут с тобой

**Godot-спутник: "Roguelike Survivor"**
Начинаешь в модуле 1 с квадрата на экране. К концу обучения — полноценная игра:
```
Модуль 1: Квадрат двигается по экрану (переменные, условия, циклы)
Модуль 2: Квадрат стал персонажем с классом Player (ООП)
Модуль 3: Появились враги в List<Enemy> (коллекции)
Модуль 4: Враги спавнятся волнами через события (делегаты, LINQ для поиска ближайшего)
Модуль 5: Сохранение/загрузка прогресса (файлы, JSON)
...и так далее — каждый модуль добавляет новый слой
```

**Uno-спутник: "Personal Hub"**
Начинаешь с простого Hello World. К концу — полноценное приложение:
```
Модуль 1: Одна страница с текстом (синтаксис)
Модуль 2: Страница с данными пользователя (классы, свойства)
Модуль 3: Список заметок (коллекции, ObservableCollection)
Модуль 4: Поиск и фильтрация заметок (LINQ, события)
Модуль 5: Сохранение в файл (JSON)
...и так далее
```

**Преимущество:** Ты не начинаешь с нуля каждый раз. Ты НАРАЩИВАЕШЬ существующий проект. Это:
- Реалистичнее (так работают в реальных компаниях)
- Мотивирующее (видишь рост проекта)
- Учит рефакторингу (переписываешь старый код когда узнаёшь лучший способ)
- Учит работать с legacy-кодом (свой код 2-месячной давности)

**Отдельные задачи из плана всё равно делай** — но как эксперименты, а не как основные проекты. Основа — два спутника.

## 4. ЧТО Я БЫ УБРАЛ ИЛИ ОТЛОЖИЛ

### Убрать из основного пути (изучить только при необходимости):
- **unsafe код, указатели (6.5)** — 99% C#-разработчиков никогда не используют. Изучи когда реально понадобится.
- **Expression Trees (6.1)** — слишком нишевая тема для начала. Отложи.
- **gRPC (13.4)** — пока не делаешь микросервисы, не нужен.
- **SIMD/Vectorization (16.2)** — экстремальная оптимизация. Отложи.
- **Visitor pattern** — самый сложный и редко используемый паттерн. Пропусти.

### Перенести на "после основного пути":
- **Docker (17.4)** — нужен только для деплоя бэкенда
- **Microservices (19.7)** — преждевременно без опыта
- **Source Generators (19.1)** — продвинутая тема

### Почему это важно:
**Cognitive overload** — когда мозг перегружен, ты перестаёшь усваивать вообще всё. Лучше знать 80% тем на уровне "могу использовать", чем 100% тем на уровне "где-то слышал".

## 5. ЧТО Я БЫ ДОБАВИЛ

### 5.1 Чтение чужого кода (КРИТИЧЕСКИ ВАЖНО)

В плане 100% — написание кода. Но в реальной работе 70% времени — чтение чужого кода.

**Упражнение (каждую неделю):**
1. Зайди на GitHub
2. Найди open-source проект на C# (Godot-плагин или Uno-приложение)
3. Потрать 30 минут на чтение кода
4. Ответь:
   - Какая архитектура используется?
   - Какие паттерны ты узнаёшь?
   - Что бы ты сделал по-другому?

**Рекомендуемые репозитории для чтения:**
- Godot C# demos: https://github.com/godotengine/godot-demo-projects
- Uno Platform samples: https://github.com/nicholasiasso/uno-samples
- CommunityToolkit.MVVM: https://github.com/CommunityToolkit/dotnet
- Небольшие C# проекты с чистым кодом

### 5.2 Навык решения проблем (Problem Solving)

Синтаксис — это алфавит. Но быть программистом — это уметь РЕШАТЬ ПРОБЛЕМЫ.

**Метод UAPC (для каждой задачи):**
```
U — Understand (Пойми задачу. Переформулируй своими словами.)
A — Approach (Продумай подход ПЕРЕД написанием кода. Нарисуй на бумаге.)
P — Plan (Разбей на маленькие шаги. Каждый шаг — 1-5 строк кода.)
C — Code (Теперь пиши код. Шаг за шагом.)
```

**Когда застрял (и перед тем как гуглить):**
1. Перечитай ошибку ВНИМАТЕЛЬНО (80% ответов — в тексте ошибки)
2. Добавь breakpoint и пройди код по шагам
3. Объясни проблему вслух (rubber duck debugging)
4. Упрости: убери всё лишнее, оставь минимальный воспроизводимый случай
5. ТОЛЬКО ТЕПЕРЬ гугли / спрашивай

### 5.3 Система отслеживания прогресса

Создай файл `PROGRESS.md`:

```markdown
## Текущий статус
- Этап: 1 / 9
- Модуль: 1.3 Операторы
- Дней подряд: 12 🔥
- Всего часов: 34

## Проекты-спутники
- Roguelike Survivor: персонаж двигается, есть враги
- Personal Hub: одна страница с заметками

## Что выучил на этой неделе
- switch expressions — мощнее чем я думал
- Разница между `override` и `new`

## С чем были трудности
- async/await — пока не до конца понимаю state machine
- LINQ GroupBy — нужно больше практики

## Что повторить
- [ ] Nullable types (через 3 дня)
- [ ] Pattern matching (через 7 дней)
```

## 6. ОШИБКИ, КОТОРЫЕ ТЫ ОБЯЗАТЕЛЬНО СОВЕРШИШЬ

Я предупреждаю заранее, чтобы ты не терял на них недели:

### 6.1 "Ловушка туториалов"
Смотришь видео, повторяешь за автором, чувствуешь что понимаешь. Закрываешь видео — не можешь написать ничего сам.

**Лечение:** После каждого туториала — закрой его и сделай ТО ЖЕ САМОЕ с нуля по памяти. Не подсматривая. Если не получилось — ХОРОШО, теперь ты знаешь что именно не понял.

### 6.2 "Ловушка идеального кода"
Перфекционизм: "я не буду двигаться дальше пока не напишу идеально".

**Лечение:** Первая версия ДОЛЖНА быть плохой. Это нормально. Ты вернёшься и перепишешь, когда узнаешь больше. Это называется "рефакторинг" и это часть работы программиста.

### 6.3 "Ловушка сравнения"
"Все на YouTube уже делают крутые игры, а я ещё на массивах сижу".

**Лечение:** Они тоже сидели на массивах. Ты видишь их результат, а не их путь. Сравнивай себя только с собой вчерашним.

### 6.4 "Ловушка широты"
"О, а ещё есть Blazor! И MAUI! И Unity! Может и их изучить?"

**Лечение:** НЕТ. Uno Platform + Godot + C#. Точка. Добавишь другое ПОСЛЕ того как станешь уверенным в этих двух. Разбрасывание = нулевой результат везде.

### 6.5 "Ловушка застоя"
Прошёл 2 месяца, кажется что ничего не знаешь, хочется бросить.

**Лечение:** Открой свой код с первой недели. Посмотри на него. Ты увидишь насколько ты вырос. Это называется "плато обучения" — после него идёт резкий рост. НЕ БРОСАЙ на плато.

## 7. СИСТЕМА ВОЗНАГРАЖДЕНИЙ (СЕРЬЁЗНО)

Мозг работает на дофамине. Без наград — нет мотивации.

### Микро-награды (каждый день):
- Записал что выучил в PROGRESS.md → ✅ (чувство завершённости)
- Написал работающий код → запусти его и ПОСМОТРИ на результат (это и есть награда)

### Недельные награды:
- Закончил все задачи недели → позволь себе что-то приятное (без экранов)
- Поддерживай streak (серию дней подряд) — не ломай цепочку

### Milestone-награды (каждый этап):
- Закончил Этап 1 → покажи проект другу или запости в сообщество
- Закончил Этап 3 → ты уже можешь называть себя "Junior C# Developer"
- Закончил Этап 6 → участвуй в game jam
- Закончил Этап 9 → ты конкурентоспособен на рынке

## 9. КОГДА ОБРАЩАТЬСЯ КО МНЕ (AI-ментору)

### ХОРОШЕЕ использование:
- "Объясни мне async/await как для 10-летнего"
- "Вот мой код, что можно улучшить?" (код-ревью)
- "Я застрял на ошибке [текст ошибки], помоги разобраться"
- "Дай мне ещё 3 задачи на LINQ средней сложности"
- "Пройди со мной тему 2.3 Полиморфизм"
- "Проверь моё понимание: [объяснение своими словами]"

### ПЛОХОЕ использование:
- "Напиши мне код для задачи X" (ты ничему не научишься)
- "Объясни мне всё про C#" (слишком широко, начни с конкретной темы)
- Копирование кода без понимания

### Идеальный процесс работы со мной:
1. Прочитай тему самостоятельно (документация)
2. Попробуй сделать задачу сам (минимум 15-20 минут)
3. Если застрял — спроси конкретный вопрос
4. Я объясню и помогу, но НЕ напишу за тебя
5. Ты доделаешь сам
6. Покажи результат — я сделаю код-ревью

## 10. ФИНАЛЬНЫЙ СОВЕТ

Самый главный навык программиста — не знание синтаксиса.
Это **способность не сдаваться когда ничего не работает.**

Каждый профессионал прошёл через:
- "Я тупой, это не для меня" (нет, ты нормальный)
- "Этот код не работает уже 3 часа" (бывает)
- "Я ничего не понимаю" (значит ты на границе роста)

Разница между тем кто стал профессионалом и тем кто нет —
первый просто не бросил.

**Не бросай.**
